Find the standards that apply, not the ones that sound alike

An agent writing architecture-as-code needs every requirement that governs the component it is building. The Open Knowledge Format (OKF) lets you store standards as linked, tagged Markdown files, so the agent can filter and walk to the right controls instead of hoping a similarity search ranks them high. This page builds the idea from the ground up.

Read the original OKF announcement ↗

Similarity search cannot tell what applies

Retrieval-augmented generation (RAG) splits documents into chunks, turns each into a vector, and returns the chunks closest to the question. That works when the answer sounds like the question. A standard often does not. A control requiring customer-managed encryption keys (CMK) for stores holding personal data applies to a bucket of customer statements whether or not the agent ever types "encryption".

Three things go wrong. Top-k ranking can drop a control that applies, and an empty result looks the same as "nothing applies". Conditions do not combine: a chunk saying "object stores" ranks just as high for a bucket of public marketing images. And status is invisible, so a superseded version reads like the current one.

Applicability is a set of conditions on the component, so it should be evaluated like a query, not guessed like a search.

OKF requires one field and little else

Google Cloud published OKF v0.1 in June 2026 as an open, vendor-neutral specification. A bundle is a directory of Markdown files, each topped with YAML frontmatter (a short block of key–value fields). It formalizes the "LLM wiki" pattern so that bundles from different producers can be read by different agents without translation. [Intro; How OKF works]

Only one field, type, is required. title, description, resource, tags and timestamp are the common optional ones, and producers may add their own. Each file's path is its identity; ordinary Markdown links between files form a graph; an optional index.md per folder lets an agent read a summary before drilling down, and an optional log.md records history. [The design in one screen]

The design rests on three principles: minimal opinion, independence of whoever writes the knowledge from whoever reads it, and "format, not platform" — no required cloud, database, model or SDK. [Three principles] What OKF is not: it is not a retrieval engine, not an ontology, and not a governance process. It gives you somewhere disciplined to put those things.

Because the spec mandates almost nothing, your house schema becomes the real contract.

Each requirement is a file that says where it applies

Model each standards domain as a bundle in Git. Folders follow the questions an agent asks; type names the kind of thing. Architecture-as-code here means describing a system as structured, machine-checkable data. FINOS CALM (Common Architecture Language Model) is one such open format: nodes, relationships and metadata in JSON that tooling can validate. [What is CALM] CALM node types make a natural join key.

standards/
├── index.md       # domains, precedence, how to navigate
├── vocab/         # closed lists of allowed values
├── requirements/  # type: Requirement (one testable control)
├── components/    # type: Component Class (mirrors CALM node types)
├── patterns/      # type: Pattern (approved designs)
├── rules/         # type: Enforcement Rule (OPA/Cedar)
└── exceptions/    # type: Exception (scoped, expiring)
---
type: Requirement
req_id: DATA-ENC-007
scope: firm
severity: must
status: active
supersedes: DATA-ENC-003
applies_to: [data-store]
data_classes: [pii, confidential]
jurisdictions: [us, eu]
enforced_by: rules/kms-cmk-required.md
---
Any store holding PII must encrypt at rest with a customer-managed key.
Satisfied by [Encrypted object store](/patterns/encrypted-object-store.md).

Fields drive filtering, links drive traversal, and the body carries the rationale the agent needs to apply the control well rather than literally. IDs here are illustrative.

The agent filters and follows links before it searches

All four conditions pass, so the control is in scope without the word "encryption" appearing anywhere. Drop PII from the node and it falls out; the superseded DATA-ENC-003 never enters. The agent then follows enforced_by to the policy-as-code rule and the "Satisfied by" link to the pattern it should build from — two things a vector search rarely returns together.

The honest comparison: a vector store with metadata filters can reproduce the filter step. OKF's distinct contributions are the links, review in Git, version pinning, and portability between agent tools.

The risk moves from ranking to classification: a mislabelled node silently misses its controls.

Severity sets the response, and teams can only tighten rules

severity borrows the requirement keywords of RFC 2119, where MUST is an absolute requirement and SHOULD allows valid reasons to deviate if the implications are understood. [Sections 1 and 3] Give each level a behaviour: must blocks the build when its check fails; should warns and makes the agent write a justification; may is context only.

Firm, division and team standards live in separate bundles, each owned by its level. A team file declares scope: team/payments and refines: firm/DATA-ENC-007. Three rules keep the layers sane:

  1. Lower levels only tighten. They can raise should to must or add rules, never lower a must; CI compares each refines with its parent.
  2. Loosening is an exception approved upstream, linked to the parent requirement and given an expiry date.
  3. Stricter wins if a conflict slips through.

The agent loads the layers its CALM context names, each pinned to a commit, and returns a refining rule next to its parent so a reviewer sees the lineage.

Borrow your taxonomy instead of building one

A taxonomy is the set of allowed values for each field; an ontology adds the relationships between them. You need far less of the second than it seems. Reuse lists that already exist and are already owned: CALM node types, the firm's data classification policy, ISO region codes, and a control catalogue such as NIST SP 800-53. [Control families]

Keep about six fields, each a closed list in vocab/, and reject unknown values in CI. Record hierarchy once — object-store is a kind of data-store — and let the retrieval tool expand queries, so files are never double-tagged. Let an agent draft frontmatter from the source policy, citing the sentence behind each tag, and have subject-matter experts approve it in a pull request. Then let misses drive change: every control the filter missed is a wrong tag, a missing value, or a missing field.

The bar is not a complete ontology; it is a taxonomy that catches more than RAG alone, which you can measure.

The agent retrieves first and cites requirement IDs through review

The enforcement rules are ordinary policy-as-code. Open Policy Agent evaluates policies written in Rego against structured input such as a CALM document [Overview]; Cedar is an alternative policy language with analysable semantics [Source]. The OKF bundle is the index that connects a prose control to the check that proves it. Wrapping filter-and-walk as a tool any agent can call keeps the logic in one place, and the human reviewer approves against requirement IDs, rules and results rather than a raw diff.

What this does not show

OKF is at v0.1, a few months old, with little tooling outside Google and no foundation governing it. [Limitations] No benchmark yet shows it beats chunked RAG for standards retrieval; the argument here is structural, and you should test it on a labelled set of designs measuring recall of applicable controls, false positives and check pass rates.

Links in Markdown are untyped, so relation meaning depends on your conventions. Decomposing policy documents into atomic, tagged requirements is expensive. Layering only works if divisions accept that they cannot quietly weaken firm standards — an organizational agreement no file format can enforce. Finally, retrieval being reproducible does not make it correct: a wrong tag gives the same wrong answer every time.

A common misconception is that OKF replaces embeddings. It does not; it narrows what search must do, and semantic search stays for questions the fields cannot express. [Section on embeddings]
